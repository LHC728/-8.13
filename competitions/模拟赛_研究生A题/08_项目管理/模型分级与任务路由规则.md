# 模型分级与任务路由规则

> 目标：高级模型负责题意、决策、分析和验收；执行模型负责已冻结任务中的重复劳动、编码、运行与整理。分级依据是任务风险，不是对模型贴永久标签。

## 1. 总原则

1. **先冻结契约，后下放执行。** 没有输入、输出、公式/规则、边界、测试样例和验收标准的任务，不得交给执行模型直接“自行完成”。
2. **编码不天然是低级任务。** 只要代码中需要决定概率口径、状态转移、优化目标、约束、指标分母、随机实验设计或结论含义，就仍是决策任务。
3. **高级模型作决定，但不能自证。** 高级模型提出的公式、路线和强结论，仍须由独立检查器、反方审计模型或人工复算验证。
4. **执行模型只能实现已批准规格。** 它可以发现问题并上报，不能静默补假设、改范围、换算法或“顺手优化”。
5. **模型名称是可替换映射。** 核心规则使用 `D/E` 能力等级；具体模型随可用性和代表性评测调整，不把治理绑定到某个会变化的产品名。
6. **人工队伍保留最终权力。** A 级题意口径、路线、论文主结论和最终提交必须由队伍确认；不能因高级模型意见一致而自动通过。

## 2. 两类模型角色

### D：Decision / Reviewer（决策与审阅模型）

适合使用当前可用的旗舰能力模型，并在确有测量收益时提高 reasoning effort。当前工作区可把高能力 `sol` 类模型视为 D 的默认候选，具体选择需在代表性任务上验证。

D 模型负责：

- 解释题意、信息边界和歧义；
- 冻结假设、状态、变量、公式、约束、指标和目标优先级；
- 比较不超过三条路线，决定最小基线和算法是否必要；
- 设计实验、随机重复、敏感性和独立检查器；
- 审查执行模型的差异、日志、失败样本与结果；
- 解释结果、控制结论强度、形成论文主线；
- 处理所有例外、冲突和变更请求。

D 模型不应长期承担：批量改名、格式转换、机械录入、重复运行、固定模板制图、按确定接口写样板代码等低判断密度工作。

### E：Execution（执行模型）

适合成本更低、速度更快的平衡或高吞吐模型。当前工作区可把 `terra` 类模型作为主要执行候选；若将来有更轻量模型，可在同一验收集通过后替换。不要仅凭“较便宜”就直接信任。

E 模型可以负责：

- 按数据字典抽取、转录、清洗和格式转换；
- 按冻结公式编写纯函数、数据类、序列化、日志和 CLI；
- 按冻结状态转移表实现离散事件框架；
- 编写已经给出预期结果的单元测试和回归测试；
- 执行参数网格、随机种子批次和 K 的全枚举；
- 按固定 schema 汇总 CSV/JSON，生成固定模板图表；
- 检查链接、文件清单、编码、命名、格式和数字一致性；
- 将冻结结果填入论文表格，但不能自行解释强弱或改写结论。

E 模型不得：

- 自行解释题面歧义或新增现实参数；
- 自行改变概率定义、状态转移、目标、约束、指标分母或终止条件；
- 在基线未失败时引入新算法或第三方依赖；
- 因测试不通过而修改测试期望值、放宽容差或删除边界案例；
- 只保留最好一次随机结果，或筛掉“不好看”的失败样本；
- 在没有证据时写“最优、稳健、显著、精度高、可推广”；
- 覆盖原始数据、冻结结果或另一执行模型的工作区文件。

### 2.1 当前可用模型的默认映射

> Bootstrap 2026-08-14（`AUTOPILOT-PLAN-V1.1-FINAL`）：具体产品名已从治理条款中解耦为 D/E 角色 + runtime mapping。旧映射（`gpt-5.6-terra`/`gpt-5.6-sol`）仅保留为历史参考，当前 Pilot #1 runtime mapping 冻结为：E/E1/E2 = `deepseek-v4-flash`（high），D/YELLOW、D/Macro = `deepseek-v4-pro`（high）。映射更新不改变 D/E 风险规则。

| 工作等级 | 角色 | Pilot #1 runtime mapping | 说明 |
|---|---|---|---|
| L0 | 脚本/机械 | 确定性脚本优先；否则 `deepseek-v4-flash`，low/medium | 机械、高吞吐；仍须自动验收 |
| L1 | E | `deepseek-v4-flash`，medium/high | 规格化编码、批量运行和固定汇总的默认档 |
| L2 | E1/E2 | `deepseek-v4-flash`，high | 仅在完整任务包和小实例已冻结后使用；**L2-GREEN 可自动放行（10 条条件，见 AUTOPILOT-PLAN-V1.1 §2.3），不强制 D**；YELLOW 才 fresh D 只读审阅 |
| L3 | D | `deepseek-v4-pro`，high | 公式、状态、实验与策略设计；强度是否上调以代表性评测为准 |
| L4 | D + D-red | `deepseek-v4-pro`，high；必要时 D-red | 质量优先的路线、口径、最终数字和结论；另开独立 D-red 并人工签字 |

这只是当前 mapping。若未来模型、价格或可用性变化，保留 D/E 与 L0–L4 规则，只更新 runtime mapping。不要默认“最高 reasoning effort 必然最好”。

### 2.2 子 Agent 调用透明协议（`SA-V1.0`）

本节约束 Codex 主 Agent 对子 Agent 的实际调用。它补充 D/E 与 L0–L4 路由，不替代冻结任务包。

#### 调用前：必须公开派单标签

每次调用前，主 Agent 必须先在 commentary 中向用户给出以下字段；同一批并行任务可合并为一张表：

```text
SUBAGENT_DISPATCH
name: 唯一且能体现职责的名称
role: E1 | E2/checker | D-red | read-only auditor | runner | reporter
level: L0 | L1 | L2 | L3 | L4
task_type: 机械整理 | 规格化编码 | 受控编码 | 决策分析 | 独立审计
model_request: 精确请求模型，或 INHERIT
model_source: explicit_override | inherited_unverified
reasoning_effort: low | medium | high | xhigh | max | inherited
selection_reason: 为什么该档足够；若使用高于默认档，说明低档为何不足
context_mode: none | bounded:<turns> | all
read_paths: 明确路径
write_paths: 明确路径或 NONE
may_spawn_children: false（默认）
```

用户看到的是**调度请求和可验证状态**，不是无法验证的后台断言：

- 显式设置 `model` 时，写“已向调度器显式请求 `<model>`”；除非工具另行返回运行时身份，不得声称后台型号已被独立证明。
- 未显式设置 `model` 时，只能写“继承主 Agent，精确型号未独立验证”。
- 若模型请求失败、被平台拒绝或实际改用继承，必须立即更正记录，不能继续沿用计划型号。
- 需要显式模型覆盖时，应使用允许覆盖的无上下文或有界上下文 fork，并在任务包中携带所需冻结材料；若必须使用完整历史继承，则接受并披露 `inherited_unverified`。

#### 路由优先级

1. L0 先判断能否用确定性脚本完成；能用脚本时，不为“有子 Agent”而调用模型。
2. L0/L1 默认 `deepseek-v4-flash`（Pilot #1 mapping）；L2 在完整规格、小例和验收均冻结后使用 `deepseek-v4-flash` high，并按 `AUTOPILOT-PLAN-V1.1-FINAL` §2.3 判定 L2-GREEN/YELLOW/RED（GREEN 不强制 D）。
3. L3/L4 才默认使用 `deepseek-v4-pro`（D 角色）。机械任务若使用 Pro，派单标签必须写明脚本或 Flash 无法安全完成的具体原因。
4. 不因任务紧急而降低语义风险等级；可通过拆分把机械部分降为 L0/L1，但决策部分仍由 D 处理。

#### 层级、并行和信息隔离

- 子 Agent 默认不得继续生成子 Agent。只有任务包将 `may_spawn_children` 设为 `true`，并同时给出 `max_children`、每个下级任务的模型范围、文件所有权和验收方式时才可多级委派。
- 一个文件同一时刻只能有一个写入 Agent。其他并行 Agent 必须只读或写入互不重叠的文件。
- E1 主实现者与 E2/checker 不能是同一 Agent 实例。checker 的上下文只包含冻结契约、canonical 参数、schema、原始输出和必要日志，不包含 E1 的推理摘要或核心实现说明。
- `followup_task` 不得被用来悄悄扩大原任务范围；若改变模型、等级、写入路径或目标，按新派单重新披露。

#### 调用后：必须汇报实际使用清单

每个子 Agent 完成、被中断或失败后，主 Agent 必须在最终答复或阶段更新中给出：

| 字段 | 必填内容 |
|---|---|
| Agent | 名称与 Agent ID |
| 模型 | 显式请求值，或“继承主 Agent” |
| 可验证性 | `explicit_request_sent`、`inherited_unverified` 或工具实际返回的身份 |
| reasoning effort | 请求值或继承 |
| 等级/角色 | L0–L4 与 E1/E2/D-red 等 |
| 任务 | 实际完成范围，不照抄原计划掩盖偏离 |
| 写入 | 修改文件；只读则写 NONE |
| 验收 | PASS/PARTIAL/BLOCKED 及证据 |
| 下级 Agent | NONE，或逐个列出并套用同样字段 |

未产出文件的只读审计也必须登记。子 Agent 的流畅回答不等于验收通过。

## 3. 任务风险分级与默认路由

| 等级 | 判断标准 | 典型任务 | 默认路由 | 放行条件 |
|---|---|---|---|---|
| L0 机械 | 输出几乎唯一，不需领域判断 | 文件清单、哈希、改名、格式化、固定模板转换 | E 单独执行 | 自动检查通过 |
| L1 规格化执行 | 有完整规格和测试，局部错误易发现 | 数据解析、纯函数、schema、批量运行、固定图表 | E 实现，E 自检 | 单元/回归测试 + 差异审查 |
| L2 受控编码 | 代码复杂但数学与接口已冻结 | DES 事件队列、资源管理、批量仿真、日志输出 | E 实现 + 独立 E2/检查器 | 小实例对拍 + 独立检查器；L2-GREEN 满足 10 条条件时自动放行（AUTOPILOT-PLAN-V1.1 §2.3），否则 YELLOW 升 D 审阅 |
| L3 分析/设计 | 存在多种合理答案，错误可能静默改变问题 | 概率模型、状态转移、调度策略、实验设计、目标与指标 | D 主做；E 只辅助检索/实现 | 人工确认 + 异源核查 |
| L4 高风险决策 | 影响全题路线、最终数字或论文强结论 | 未冻题意/状态机、路线、最优 K 规则、结论与建议、数字冻结 | D 提案，另一 D/红队审计，人工签字 | 双模型异议关闭 + 队伍签字 |

如果无法确定等级，按高一级处理。任务可以拆分：例如“确定故障 CDF”是 L3/L4，“按已冻结 CDF 写采样器”是 L1/L2。

## 4. 决策点与执行点的判定问句

下列任一问题回答“是”，任务就不能整体下放给 E：

1. 不同实现会代表不同的题意或现实机制吗？
2. 需要选择公式、算法、权重、阈值、容差、随机重复数或停止规则吗？
3. 失败后存在两种以上合理处理，而且规格没有规定吗？
4. 输出会直接进入表 2、摘要、结论或“最优”声明吗？
5. 错误可能让程序正常运行却得到错误答案吗？
6. 是否需要新增数据、依赖、假设或改变文件 schema？

若答案全为“否”，且验收条件可机器检查，才可作为 E 任务。

### 4.1 最容易伪装成编码细节的决策

下列事项只要未在任务包中写明，就必须升级给 D，E 不得选择“常见默认值”：

- 同一时刻多个事件的处理优先级；
- 时间区间左闭右开、边界相等时算完成还是中断；
- 浮点比较容差、时间取整和输出精度；
- 缺失值、异常值、未知类别和空结果的处理；
- 随机数生成器、子流拆分、抽样方法和不同策略间随机数配对；
- CDF 插值、分布尾部、条件概率和多事件同时发生的规则；
- 任务取消、恢复、重启和已耗时间/设备年龄如何记账；
- 资源冲突、派工平局、队列优先级和饥饿处理；
- 指标分母、班次数、末班、失败样本和终止时刻的统计口径；
- 搜索空间、网格步长、停止规则、置信区间和重复数；
- 为提高性能而采用的截断、缓存、近似、并行顺序或降采样。

## 5. 标准派单包

D 向 E 派任务时必须提供以下字段；缺一项，E 应暂停并请求补齐，而不是猜测。

```yaml
task_id: E-YYYYMMDD-序号
level: L0 | L1 | L2
objective: 一句话说明唯一目标
allowed_files:
  read: [明确路径]
  write: [明确路径]
frozen_inputs:
  parameter_version: 版本或哈希
  assumptions: [A01, A02, ...]
specification:
  formulas_or_state_transitions: 明确引用位置
  input_schema: 字段、类型、单位、范围
  output_schema: 文件、字段、类型、排序、精度
  error_behavior: 对缺失、越界、冲突如何失败
must_not_change:
  - 目标、约束、指标和概率口径
  - 冻结输入与测试期望
acceptance:
  commands: [可复现命令]
  tests: [测试名称和预期]
  invariants: [必须始终满足的条件]
evidence_to_return:
  - 修改文件清单和差异摘要
  - 实际运行命令、退出码和输出路径
  - 失败/警告/未完成项
escalation_triggers: [本规则第6节]
```

禁止使用“把模型做完”“优化一下代码”“根据题意自行处理”等开放式派单。

可直接复制的文件模板见 [执行模型派单模板.yaml](执行模型派单模板.yaml)。

## 6. E 模型强制升级触发器

出现以下任一情形，E 必须停止当前分支、保留已完成证据，并向 D 提交 `BLOCKED/DECISION_REQUIRED`：

- 规格、数据字典、测试或两个来源互相矛盾；
- 发现 A01–A09/B01–B19 与权威口径冲突，或需要解释尚未签字的实现边界/新增假设；
- 需要改变公式、状态转移、约束、指标、随机机制或目标；
- 测试失败，且修复可能需要改变预期值、容差或数据；
- 遇到题面未覆盖的状态、资源冲突或边界事件；
- 需要新增依赖、外部数据、联网信息或超出允许文件；
- 实际输出与基线、手算或独立检查器不一致；
- 预计改动范围超过派单文件，或发现上游设计缺陷；
- 结果会改变路线、推荐 K、论文主表或强结论；
- 同一错误连续修复两次仍失败。

升级报告只需包含：触发器、最小复现、已知事实、两个以内候选处理及各自影响；E 不替 D 选择。

对 E 的首要评价不是“尽量不提问”，而是**能否识别未指定行为并及时升级**。静默猜测后交出可运行代码，比主动阻断更严重。

## 7. E 模型交付格式

E 完成任务时必须返回：

```text
STATUS: PASS | PARTIAL | BLOCKED
SCOPE: 实际读取/修改文件
CHANGES: 机械描述，不写“效果良好”
RUNS: 实际命令、退出码、随机种子/参数版本
TESTS: 通过数、失败数及失败名称
OUTPUTS: 生成文件及行数/尺寸/哈希（适用时）
DEVIATIONS: 相对规格的任何偏离；无则写 NONE
WARNINGS: 数据、数值、性能或边界警告
DECISIONS_MADE: 必须为 NONE；否则任务自动升级
```

没有实际运行证据的“代码已完成”视为未交付。

## 8. 三层验收

任何一层失败都阻断合并和结果冻结，不能用后一层的主观判断覆盖前一层失败。

### 8.1 实现者自检（E1）

- 按任务包运行全部命令、单元测试和静态检查；
- 报告全部失败、警告、种子、参数版本和偏离；
- 自检只能证明实现者知道发生了什么，不能证明模型正确。

### 8.2 独立执行验收（E2/checker）

- 语法、格式、类型、schema 和文件范围；
- 单元/回归测试与固定小实例；
- 重现命令、随机种子、行数、哈希和输出完整性；
- 不变量：概率范围、资源容量、前置、班界、终止和指标范围。

E2 必须独立读取题面/冻结规格和原始输出，不复用 E1 的解释、推理或总结；能只读就不修改。

### 8.3 语义验收（必须由 D 完成）

- 实现是否仍回答冻结的问题；
- 是否偷偷新增假设、改变口径或把近似写成事实；
- 数值差异是否有机制解释；
- 检查器是否与主模型异源；
- 结果能支持多强的论文结论；
- 是否需要触发变更控制。

关键决策还须保留至少一个替代解释和能区分二者的可证伪测试。L3/L4 结果必须再经过人工队员签字。D 的“看起来合理”不是验收证据。

## 9. 主模型、检查器与论文的隔离

| 通道 | 可由谁实现 | 谁定义规格 | 禁止事项 |
|---|---|---|---|
| 主模型 | E1 | D + 队伍 | 自行修改问题契约；输出“验证通过”替代检查 |
| 独立检查器 | E2 或 D-red | D 单独给原始契约和接口 | 导入主模型判断/指标函数；照抄 E1 实现 |
| 批量运行/汇总 | E-runner | D 冻结实验表 | 改种子、删失败、只报最好一次 |
| 图表/表格 | E-report | D 冻结字段和图意 | 手填数字、改变指标、选择性隐藏情景 |
| 结果解释/论文主结论 | D | 队伍确认 | 让 E 根据图形自行写强结论 |

同一模型实例不得同时充当主模型作者和最终检查器。若模型资源有限，至少更换上下文，并让检查器只看到原始契约与输出，不看主模型推理和实现摘要。

## 10. 并行与文件所有权

- 只有输入已冻结、输出文件互不重叠的 L0–L2 任务可以并行。
- 每个任务有唯一写入目录或明确文件所有者；两个 E 不得同时改同一文件。
- 共享 schema、公共状态类和参数配置先由一个任务完成并验收，再扇出并行任务。
- 并行任务只交换已版本化的文件，不通过聊天复制未冻结数字。
- 合并由 D 或指定集成任务完成；执行模型不得为解决冲突自行选择业务口径。
- 每个任务包记录契约版本和关键输入哈希；审计通道只接收题面、冻结规格和原始输出，不接收实现者的推理摘要，降低上下文污染。

## 11. 变更控制

任何对 A01–A09、参数字典、输出 schema、指标公式、随机计划或检查器不变量的修改，都要：

1. 创建变更 ID，写明原因和影响的小问/文件；
2. 由 D 分析是否需要重跑哪些基线、实验、检查和图表；
3. 队伍确认后更新版本；
4. 旧结果保留但标记 `superseded`，不得覆盖；
5. E 只能在新版本生效后继续。

契约或关键输入变更后，引用旧版本的未完成任务自动失效；旧运行结果不得继续进入汇总，除非 D 明确证明该变更与结果无关并留下记录。

## 12. 低级模型是否够用：代表性评测

在正式批量使用某个 E 模型前，用本题的代表性任务做一次小评测：

1. 从 `parameters.csv` 读取并验证当前 64 条参数记录、12 列和概率/单位范围；其中 `待求/待确认` 只允许出现在已登记的派生参数行；
2. 按冻结规则实现一个纯概率函数并通过边界测试；
3. 实现 1 台无异常事件小例，与手算时间线一致；
4. 生成规定 schema 的事件日志；
5. 面对一条故意矛盾的规格时，能升级而不是自行猜测。

五项全过才进入 L2；否则只安排 L0/L1。模型升级或提示模板变化后重跑同一评测。比较正确率、返工次数、人工审阅时间、延迟和成本，而不是只看单次回答流畅度。官方 OpenAI 模型指南也建议在代表性工作负载上比较质量、延迟与成本，并把高推理/Pro 模式留给确有质量收益的困难任务。
